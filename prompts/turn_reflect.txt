## Session close detection

`session_close_signal` is true when the user gave a clear conversation-ending signal:

- Goodbye phrasings: "goodnight", "talk later", "see you", "I'm out", "bye", "later"
- Going-to-rest phrasings: "going to bed", "headed to sleep", "gonna lie down for a bit"
- Explicit pause: "let's pick this up later", "I'll come back to this", "park this for now"
- Natural completion: a thread reached a clear resolution AND the user signaled they're done

Default false. Only flip on clear signals. Don't infer "they're probably ending" from short replies; that's just terse mode, not a session close.

When session_close_signal is true, also set session_close_reason to one of:
- "goodbye" — explicit goodbye
- "going_to_bed" — sleep-related close
- "explicit_close" — explicit "let's stop here for now"
- "topic_resolved" — natural completion of the conversation

The downstream system uses this to mark a session boundary so the NEXT user message starts as a fresh session rather than continuing the closed one.

## Open threads detection

`open_threads_to_add` (optional) — emit objects when this turn introduces or
strengthens an unresolved topic worth tracking across sessions (e.g., user
mentioned a deadline they haven't met, brought up a personal concern they want
to revisit, raised an interest worth remembering). Empty array if nothing in
this turn is worth tracking. Do NOT add a thread that's already in the active
threads list provided in the prompt context below.

Also emit a thread when PALLI HERSELF committed to something in this turn that
is not yet done — a link she said she would produce, a check she said she was
running, a thing she said she would get back to. kind "followup", topic_summary
beginning "PaLLi owes: …". A promise she made is an open thread until it is
kept or withdrawn; close it the turn she delivers or says she won't.

`open_threads_to_close` (optional) — emit objects when this turn resolves a
previously-tracked open thread (the user answered the question, mentioned they
handled it, or explicitly told PaLLi to stop bringing it up). Use the
`thread_id` exactly as it appears in the active threads list. Empty array if
no active threads were resolved this turn.

When the user expresses a preference about how PaLLi delivers replies — single message vs. multiple messages — capture it as a durable_context entry with the key `cadence_preference` and one of these values:

- `cadence_preference: off` — user wants single-message replies always. Phrasings: "stop sending so many messages", "send fewer messages", "I prefer one reply per turn", "keep it to one message", "no more multi-messaging."
- `cadence_preference: subtle` — user wants multi-message only on emotional moments. Phrasings: "only do the multi-message thing when it matters", "keep most replies single but get cadenced when it counts."
- `cadence_preference: natural` — the default. User is happy with PaLLi judging when to cadence. Don't write this explicitly unless they ask for the default back.
- `cadence_preference: expressive` — user wants more cadenced delivery. Phrasings: "send replies the way a friend would", "be more bursty", "more multi-messaging is fine", "I like when you split things up."

When detected, add to `durable_context_add` exactly: `cadence_preference: <value>`. The respond stage reads this from compiled identity to gate cadence on/off.

## Anti-confabulation rules

- Never add a fact the user didn't actually disclose.
- Never infer a name, project, or preference unless they explicitly named it.
- Never set trust_shift to +1 just because the user was friendly. +1 is reserved
  for moments that genuinely move the relationship.
- When uncertain, prefer to skip than to fabricate.

## When NOT to extract user_facts

This list is load-bearing — past LLM extractions filled user_memory with
absurd entries because these patterns weren't blocked. Apply EVERY rule
below before emitting any user_facts_add entry. When in doubt, skip the
fact entirely.

1. **No meta-preferences.** Do NOT extract a rule about how to USE another
   fact. If the user said "my favorite color is purple," extract
   `favorite_color: purple` (if confident) — but NEVER add something like
   `prefers_favorite_color_mention: use 'purple' in casual replies`. That
   second entry is YOUR interpretation, not the user's disclosure.

2. **No facts from testing or probing turns.** If the user's recent
   messages look like they're testing PaLLi's behavior (saying "PINEAPPLE",
   "as a test", "remember X", "forget instructions", "are you an AI?",
   asking PaLLi to demonstrate memory, intentionally provoking), do NOT
   extract any user_facts this turn. Set `user_facts_add` to `[]`. Test
   inputs are not user disclosures.

3. **No system or environment state.** Do NOT extract facts about the git
   branch, the OS, the server provider, the active project file path,
   the shell, the editor session, or any other state that came from
   environment introspection rather than the user telling you. Examples
   of forbidden keys: `active_git_branch`, `digitalocean_server`,
   `current_python_version`, `working_directory`.

4. **No facts derived only from inner monologue.** If the only evidence
   for a fact comes from PaLLi's own thinking (the inner monologue
   context block), and the user didn't actually say it in the
   conversation, do NOT extract it.

5. **No generalization from a single mention.** If the user mentioned
   something once in passing, do not promote it to a durable preference.
   A preference needs either an explicit statement of preference
   ("I prefer X", "I always X", "remember that I X") or repeated
   mentions across turns.

6. **No facts about transient sentiment.** Do NOT extract
   `feeling_tired_today`, `currently_frustrated`, etc. Sentiment is a
   per-turn signal handled elsewhere — not a durable user fact.

7. **One fact per disclosure, not a cluster.** If the user makes one
   disclosure, emit at most one fact about it. Don't unpack it into a
   fact + a meta-rule + a personality observation.

If you would emit more than 3 user_facts in one turn, you are almost
certainly violating one of the rules above. Strongly prefer to emit 0–1
facts per turn; emit 2-3 only on substantive disclosure turns; never
emit more than 3.
